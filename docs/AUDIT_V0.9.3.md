# 共造 v0.9.3 全流程质询与验收记录

2026 年 11 月 11 日。基线为已发布的 v0.9.2。检查对象包括浏览器和小程序客户流程、商家报价、设备网关、生产台账、订单状态、账号隔离、存储和发布包。本文中的订单、资金和机器派发均在沙盒中验证。

## 直接影响客户和商家的问题

| 质询 | 发现与修复 | 复验 |
| --- | --- | --- |
| 商家能在一板打几十件，换成小机器会不会少收钱？ | 旧算法按默认大板估算。现在使用所选商家的成型范围，并按计算板数分摊批量成本。 | 同一批 7 件、每件占地 72 × 48 mm，选 90 × 90 mm 成型范围时按 7 板计价。 |
| 估价依据是几何推算，还是已经运行过切片器？ | 前端曾对已有切片证据的价格仍写“未切片”。现在分别显示计算来源。匹配时核对模型版本、数量、单位、商家设备和工艺。 | 不同设备或版本的结果不能用于本单。已取得切片板数而没有每板容量时，页面仅显示有依据的数字。 |
| 商家人工调价后能否看到最终确认的利润？ | 人工方案检查切片成本和工时底线，订单从客户接受的那一版方案读取制造价格与成本。 | 回归例中，制造价 1,000 元，估算成本 600 元，显示预计毛利率 40%。实际利润还取决于实耗、人工和返工。 |
| 上传远离坐标原点的小零件、开口模型会怎样？ | 修复微小 STL 体积计算误差。不同曲面绕向导致体积不能可靠解释时，转工程审核。网页保留可解析的网格和尺寸。 | 通过远坐标微小立方体、反向曲面和开口 STL 用例，既有已成交订单保留自己的模型与金额快照。 |
| 客户输入 1.5 件或 51 件会发生什么？ | 网页原先可能静默更改件数。现在保留输入、定位数量框，明确允许 1–50 的整数。 | 浏览器实测 1.5 和 51 均被拦下，修改为 7 后错误清除并进入地址补填流程。 |
| 国际地址失败时能否改对？快速切换需求会不会看到旧报价？ | 小程序支持逐字段提示，识别已支持的国家代码。微信服务端样件尺寸、件数限制与平台一致。结果返回时重新核对当前请求。 | 覆盖中国与海外地址、输入国家代码、晚到的报价结果和错误保留。小程序真机登录、显示仍待现场验收。 |
| 客户在两个标签切换账号，旧地址会保存给谁？ | 页面将写操作和重试绑定到打开时的工作空间，服务端使用已认证身份进行核对。访客与已注册账号分开展示。 | 两个测试账号、同一浏览器会话语义及本地 SQLite 验证，切换后的旧表单被拒绝，新账号重新填写后可保存。 |
| 较早的设备扫描能把离线设备重新变为在线吗？ | 导入以网关最新观察为准，过时记录不能覆盖新状态。协议探测明确显示抽查几台、配置几台。 | 合成的在线、离线、延迟报告和不同网关相互隔离场景通过。 |
| 下单确认了某台设备或切片，后来会不会派到另一台？ | 两条模拟派工路径都核对承诺的设备和切片。维护中设备不预占材料。历史方案缺快照时核对当时配置版本。 | 覆盖首次下单、排队重派、模板改版、旧单和库存释放。 |
| 计算服务断线或重启，后面的任务能继续吗？ | 失效租约及已更换模板的回执能得到处理，网络抖动重试沿用任务身份。队列满时先检查已有相同任务。 | 用离线工艺和合成回执覆盖恢复、去重和满队列。 |
| 已开工的客户申请退款，是否会永远卡在打印中？ | 待退款期间可登记已发生的实耗、取件质检并释放机器，然后处理退款。已有争议也可撤回。 | 从上传 STL、接受报价到生产中退款，17 次本地 HTTP 请求走完流程，核对耗材、设备和退款终态。 |
| 承运商签收是否会提前放款？签收后还能看运单吗？ | 签收、客户验收、模拟结算分别记录。退款成功后不能再结算。已签收、已结算订单继续展示物流，过滤付款和生产事件。 | 复验签收与验收、退款和结算竞争、重复提交。外部测试响应若运单号不匹配会被拒绝，缺失运费显示待定。 |
| 同一账号反复询价会耗尽空间吗？ | 旧版重复保存报价和回执，先于业务上限触及 1 MiB 存储上限。新版仅在需要时无损压缩报价历史，本地按账号顺序处理同时到来的报价写入。 | 同一测试条件下请求 64 次、并发 8，旧版 34 成功、30 次容量错误，新版 64 次全部成功，最终版本号与成功写入数一致。 |
| 连续更新两个版本会覆盖商家的部署配置吗？ | 更新器保留现场 AppID、原生应用标识和已修改的小程序连接配置，同时更新未改的原厂文件。新版发布清单进入备份和回滚流程。 | 覆盖连续两次升级、保留自定义配置、还原原厂文件及失败后回滚。 |

## 复查中才发现的问题

一次修复通常只覆盖一条路径。把同一问题换角色、换入口或换发生时点再次执行，发现并修复了以下遗漏。

- 生产中心已核对切片后，旧派工入口还可能先启动默认模拟设备。现在两个入口使用同一约束，受限订单等待商家在生产中心处理。
- 退款成功后，原争议标签曾盖住退款状态。现在显示资金的实际终态，已有争议单独记录，运单也保留。
- 第一次解决容量问题后，临界大小的历史可能写入成功、读回失败。最终版本在提交前检查展开后的历史大小，并保留原子写入。D1 适配器的契约测试覆盖新实例读回、两个并发修改及账号隔离。
- 在浏览器改正数量后，旧提示曾短暂留在读屏内容中。现在只有输入框旁的错误提示，改正即清除。
- 更新模板后再升级一次，原有清单曾停在旧版本。现在同一次更新会记录新清单，下一次可识别哪些文件是商家自己改过的。

## 验证结果

本次完整自动化套件共 480 项，472 项通过，0 项失败，8 项因当前环境缺少 Trimesh、OR-Tools 或 PrusaSlicer 等外部工具而跳过。跨端工程通过 287 项静态检查。Windows PowerShell、macOS 本机、Android/iOS 签名和微信发布尚待目标环境验收。

抽取 PLA、PETG、未付款工程询价和已接受的人工方案四条路径，按生产、库存占用、物流、资金和争议条件枚举出 270 个单订单状态。在这些状态和所枚举操作内，每个状态均存在通向模拟结算、退款或撤单的路径。此检查不覆盖真实资金渠道或多商家并发履约。

再次询价时，新版可利用当前账号已保存的原 STL 重新核对摘要并计算旧模型的几何数据。原件缺失时保留人工审核入口。尚未接受的旧计价方案需按新规则测算，已确认的订单保持原始快照。

## 使用与复核

从项目根目录运行 `npm test` 复验自动化用例，运行 `npm run test:load -- --requests 64 --concurrency 8` 复验本地报价突发负载。后者使用临时 SQLite 库。本地结果不能直接外推成线上商户数或吞吐量。

Windows 升级时，关闭服务并备份旧项目的 `data/` 文件夹。将新版解压到其他目录，从新目录运行 `UPDATE-WINDOWS.cmd`。旧 JSON 行可直接读回。报价历史超过旧上限并写入紧凑格式后，若需降级，须将旧代码与升级前的数据备份配套恢复。这会回到备份时间点。

本轮可交付的是经过复测的沙盒版本。表中的独立多商户、真机和资金闭环是下一阶段的开发与验收工作。
