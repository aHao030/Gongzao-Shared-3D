# 平台架构决定

当前 v0.2 已打通网页 → 统一 API → 持久化存储的服务端沙盒。本地 Node.js 24 使用 SQLite；私人托管工程使用 Worker、D1 和 R2，远端迁移与身份验证状态以发布记录为准。模型上传、服务端报价、订单及模拟履约可通过网页完成，实际实现和阶段限制见 [v0.2 实施说明](IMPLEMENTATION_V0.2.md)。

真实设备、支付渠道、物流接口及客户/商家/操作员的生产权限模型尚未接入。以下涉及受控切片、农场网关、资金回调和真实设备执行的内容是生产架构要求；现有离线网关模拟器用于验证规则，没有与沙盒 API 或真实机器连通。

## 交易与设备执行分开部署

交易模块管理模型、报价、预约、订单、支付与售后。农场网关在商家本地运行并主动连接平台，持有设备凭据，执行受控任务。顾客网页和 App 不直接访问农场局域网或打印机控制口。

这会增加网关维护工作，但避免为每台打印机开放公网入口，并使断网时的本地执行结果可以恢复。网关不能承担替代硬件急停或机器安全联锁的职责。

## 一个权威生产计划

报价与执行关联同一份不可变生产计划，记录模型哈希、单位、材料、数量、喷嘴、机器配置、工艺模板、切片器版本及输出文件哈希。切片器升级或工艺变更需要重新验证；报价确认后不静默改为另一种材料或质量。

## 按能力分级接入

监测、文件上传和远程启动分别登记。首版在经过实机认证的 FDM 范围内自动启动。树脂、金属及 CNC 先以工艺审核和现场准备确认驱动，逐型号扩展自动化，不能用“支持 Wi-Fi”推导自动生产能力。

## 业务后端与计算任务分离

正式架构建议使用关系数据库记录订单与账本、对象存储保存模型、任务队列调度切片、隔离的计算进程运行几何分析。支付/物流回调通过幂等事件持久化；数据库事务与 outbox 保证后续任务可恢复。初期采用模块化单体，避免尚无规模时拆出大量微服务。

当前网页由本地服务或托管 Worker 同源提供，并通过 API 读写持久化状态。单工作空间 JSON 与 CAS 是私人沙盒的阶段实现，不替代生产账本、事务性 outbox 或全平台资源预约。长时间切片、真实支付和农场设备任务仍由后续独立服务接入。

## 跨端复用的范围

共用领域定义、接口契约和设计 token。第一版采用独立 HTML 网页、原生微信小程序示例、Capacitor 手机容器和 Tauri 桌面容器；后续页面规模增长时可按团队能力选择 React/Taro 或 uni-app，迁移 UI 时保留服务端契约。小程序与 DOM 不共用渲染层。
